# Security

Production requires an external OIDC authority. The storefront and administration application are same-origin BFFs using authorization code flow with S256 PKCE, state, and nonce. Login transactions expire after 10 minutes. Access, refresh, and ID tokens are stored server-side in Redis; the browser cookie contains only a random session ID and is HttpOnly, SameSite=Lax, path `/`, and `Secure` with a `__Host-` name when `SESSION_COOKIE_SECURE=true`, which is required in production. Local HTTP Compose explicitly disables that flag. Sessions default to eight hours. Tokens are refreshed server-side within 30 seconds of access-token expiry; a failed refresh deletes the Redis session and the BFF returns 401.

State-changing BFF and logout requests require both an exact Origin match against canonical `APP_URL` and a timing-safe match of the session-bound `X-CSRF-Token`. The BFFs strip browser `Authorization`, `X-Customer-Id`, and `X-Admin` headers and proxy only explicit method/path allowlists. The administration BFF has separate operations and supply-chain allowlists and forwards idempotency keys only to allowlisted mutations. Public calls remain server-to-API. Cart, checkout, order, auth-session, and BFF responses are `no-store`.

The API validates signed JWT access tokens locally from OIDC discovery/JWKS: exact configured issuer and audience, signing key, expiry, required expiration and `sub`, accepted JWT types, and at most one minute of clock skew. It does not introspect each request. Metadata/JWKS are cached by the JWT middleware; an unknown signing key triggers refresh (`RefreshOnIssuerKeyNotFound=true`), so planned rotation must retain old keys through token expiry. If discovery is unavailable, already cached keys can continue validating matching unexpired tokens, but newly rotated keys cannot be learned.

Keycloak client roles for `AUTH_ROLE_CLIENT_ID` (default `commerce-api`) are normalized into permission claims and named policies. `Administration.Access` gates the admin group and identity diagnostic; catalog, operations, supplier, procurement, receiving, and invoice policies further restrict each endpoint. `Orders.ReadOwn` requires identity, while `Orders.ReadAny` grants the explicit cross-customer query path. Supplier portal routes require `Supplier.Portal`, but every query and command is also restricted by the active `supplier_users` membership; role possession alone cannot cross supplier organizations. Object ownership and business invariants remain in ASP.NET/application queries, not Keycloak. Non-owned resources return 404 where appropriate. Keycloak Authorization Services is intentionally disabled. No service-account or client-credentials identity is configured because there is currently no service caller.

An `ApplicationUser` is created on first private use and uniquely mapped by validated `(issuer, sub)`; its internal ID owns carts and orders. Names and email are bounded profile fields, not authorization identifiers. Development `X-Customer-Id` and `X-Admin` authentication is accepted only when both the ASP.NET Development environment and `ALLOW_DEVELOPMENT_IDENTITY=true` are set. Compose binds development services to loopback; these headers and imported users are not production mechanisms.

API CORS is exact: origins are the comma-separated `FRONTEND_ORIGINS` value (falling back to `FRONTEND_ORIGIN`), headers are `Accept`, `Content-Type`, `Authorization`, `Idempotency-Key`, `If-Match`, and `If-None-Match`, and methods are `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, and `OPTIONS`. Credentials are not enabled. Browser private traffic should use the same-origin BFF rather than cross-origin API cookies. Set production origins explicitly.

`APP_URL` is mandatory in production and is the canonical origin for callbacks, redirects, logout, and Origin checks; do not derive it from an untrusted Host header. The API honors `X-Forwarded-For` and `X-Forwarded-Proto` only when `TRUSTED_PROXY_IPS` contains the immediate trusted proxies. Configure the external OIDC issuer separately from optional internal metadata URLs, and use HTTPS outside Development.

Authentication failures and authorization denials are counted as `commerce.authentication.failures` and `commerce.authorization.denials`; logs record endpoint/failure type without token contents. `/health/identity` performs a three-second discovery check and requires `Administration.Access`; it is diagnostic and does not gate `/health/ready`.

The API also applies HSTS in production, CSP, frame denial, MIME sniffing protection, a request body limit, RFC 7807 errors, endpoint rate limits, bounded validation, and server-side ownership checks. Browser-supplied selling prices, totals, inventory, titles, and customer IDs are ignored. Purchase-order terms are copied from persisted supplier sources. Fiscal QR adapters allowlist provider syntax and never dereference scanned URLs; document bodies belong in object storage and only bounded references and hashes are persisted. Logs must exclude tokens, passwords, addresses, cache values, fiscal payloads, and payment data. This repository does not collect card data.

Tests cover local JWT rejection for expiry, issuer, audience, and signature; role-to-policy behavior; own/any order access; supplier membership isolation; invoice provider URL rejection; receipt idempotency and disposition accounting; OpenAPI bearer marking; and frontend CSRF, Origin, return-path, token-refresh-window, and BFF-allowlist helpers. They use an in-process static signing configuration, not a live Keycloak/JWKS flow. There is no automated end-to-end coverage yet for login, refresh rotation/concurrency, logout/revocation, Redis loss, proxy deployment, Keycloak outage, or signing-key rotation.

Production requires hardened HA OIDC and Redis deployments, TLS, managed and rotated secrets, persistent provider/database state, restricted administration, backup/restore, audit retention, alerting, canonical URL/proxy validation, and tested key/session/outage procedures. The imported `start-dev` realm, users, and Compose fallback credentials are local fixtures, not evidence of production readiness.

Checkout persists recipient and shipping-address fields in PostgreSQL. A production deployment must define access, retention, deletion, and data-subject handling before collecting real customer information.
